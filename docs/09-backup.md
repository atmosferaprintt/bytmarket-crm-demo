# Резервная копия и проверяемое восстановление

Статус: локальная эксплуатационная основа. Скрипт `scripts/backup_db.py` создаёт согласованную SQLite-копию через `sqlite3.Connection.backup`, включая зафиксированные данные из WAL. Простое копирование основного файла работающей SQLite для этой задачи не используется. Перед копированием проверяется исходная БД, после — полученная копия (`PRAGMA integrity_check`). Новая копия переводится в режим журнала DELETE и не требует отдельных файлов WAL/SHM; режим исходной БД не меняется. Восстановление создаёт отдельную БД и повторяет проверку целостности.

**Внешнее место хранения пользователь ещё не выбрал.** Каталог `backups` рядом с приложением — локальная копия, а не резерв отдельно от рабочего сервера. Скрипт ничего не отправляет в сеть. Автоматическое расписание, доставка копий на независимый носитель/сервер, шифрование, срок хранения, допустимая потеря данных и время восстановления пока не согласованы и не реализованы.

## Создать и проверить копию

Команды выполняются из корня проекта. Имена файлов ниже — пример для конкретного запуска; для следующего запуска используйте новое имя. Существующий файл назначения никогда не перезаписывается, в том числе при восстановлении.

```bash
python3 scripts/backup_db.py --source data/bytmarket.sqlite3 --destination backups/bytmarket-2026-11-05-01.sqlite3
python3 scripts/backup_db.py --verify backups/bytmarket-2026-11-05-01.sqlite3
```

Код завершения `0` и `"integrity_check": "ok"` означают успешную структурную проверку. Код `1` и сообщение в stderr означают ошибку операции. Ошибка аргументов возвращает код `2`. Отсутствующая исходная БД не создаётся автоматически. Новые файлы копий создаются с разрешениями `0600`.

## Отдельная проверка восстановления

```bash
python3 scripts/backup_db.py --restore backups/bytmarket-2026-11-05-01.sqlite3 --destination restore-check/bytmarket-restored-01.sqlite3
python3 scripts/backup_db.py --verify restore-check/bytmarket-restored-01.sqlite3
python3 app/server.py --db restore-check/bytmarket-restored-01.sqlite3 --port 8766
```

Последняя команда запускает отдельный локальный экземпляр на восстановленной БД. Его нельзя путать с рабочим экземпляром; проверочные изменения относятся только к восстановленной копии. Откройте `http://127.0.0.1:8766` в отдельном чистом профиле браузера: интерфейс загрузит восстановленный серверный демо-снимок через `/api/demo-state`. Переключателя на операционные серверные данные в интерфейсе нет. Сверьте состояние демо с контрольным снимком на момент копирования. Операционные таблицы проверяйте отдельно через `/api/state` или read-only запросы к восстановленной SQLite: товары, клиенты, заказы, строки, остатки и резервы. Не используйте браузер с неотправленными изменениями для исходной проверки восстановления: он может предложить конфликт или запись локальной версии. Не сравнивайте с уже изменившейся рабочей БД как с тем же моментом времени. После проверки остановите проверочный сервер.

Структурная целостность SQLite сама по себе не подтверждает корректность бизнес-учёта. Для каждого практического восстановления необходимо записать имя копии, время её создания/проверки, количество и суммы контрольных документов, результат сверки, длительность восстановления и выявленные расхождения. Назначение ответственного и регулярность проверки требуют согласования.

Автоматизированная проверка на временной БД:

```bash
python3 -m unittest discover -s tests -p test_backup.py -v
```

Тест действительно создаёт копию работающей БД с WAL, восстанавливает её в другой файл, сверяет количества и значения строк, записывает данные в восстановленную БД и проверяет независимость исходной копии. Дополнительно проверяются отказ перезаписи, повреждённый файл, отсутствие файла и CLI-команды. Это проверка механизма на тестовых данных; она не означает, что восстановление пользовательской рабочей БД уже выполнено.

## Возврат в рабочую эксплуатацию

Скрипт намеренно не заменяет рабочую БД автоматически. При аварии остановите процессы записи, сохраните доступные аварийные файлы для разбора, восстановите в новый путь, выполните сверку и только после решения ответственного запускайте рабочий экземпляр с новым `--db`. Перед переключением учтите операции, возникшие после снимка, и исключите одновременную работу двух расходящихся экземпляров.

Копия содержит всю SQLite, включая операционные таблицы и уже записанные серверные демо-снимки `demo_snapshots` (сервер сохраняет последние 20 ревизий). Неотправленные изменения localStorage, браузерные резервные копии конфликта/отмены сброса, исходный код, настройки и внешние документы/файлы в неё не входят. Успешная копия SQLite не подтверждает, что последняя браузерная правка успела отправиться: перед контрольной копией проверьте индикатор сохранения и серверную ревизию. Чувствительные данные внутри копии не шифруются этим скриптом; доступ к выбранному месту хранения нужно ограничить. Для готовности к эксплуатации ещё требуется независимое хранилище и проверка восстановления именно из него.
